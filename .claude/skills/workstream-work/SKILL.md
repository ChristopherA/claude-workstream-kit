# Workstream Work

Read `.state/ACTIVE.md` and the active `workstream.md` first, then announce "Resuming <name> at <task>". If the session-start hook reported a staleness signal, reconcile before any task work: update the state to match reality, set `status: paused`, or start `/workstream-close`, which stops at its own gate. If the backlog no longer reflects the accumulated Decisions and Learnings, or the critical path is not derivable from it, run `/workstream-review` before working — its restructures are user-gated, so running it commits nothing, while a drifted backlog worked as written does. The reason behind each move is in `references/failures.md` under the move's heading; read it when a move is doubted.

If ACTIVE.md refers to a goal drafted by an earlier session, treat the reference as unverified: a condition copied to the clipboard but never armed lived only in that session's chat. Say plainly that the draft is unrecoverable and derive a fresh condition — never redraft silently, which turns a lost draft into an invisible scope change.

## Verify the task against the world

A task description is a dated claim about the world, and the first step of working one is re-reading the world it describes — the named artifacts, not the backlog's wording — BEFORE drafting the goal condition, since a condition drafted against the description inherits whatever it got wrong. Three kinds of claim, the second and third the ones that read as given rather than as asserted:

- **What it names** — a file, a count, an audience size, a platform behaviour. Re-read each against the artifact.
- **Its scope** — a task's list of what it touches asserts a blast radius, and reads as scope rather than as a claim. Sweep the tree for the thing being changed — `python3 .claude/scripts/workstream-record.py cites <project root> "<the thing>" --repo` for anything the state or docs name — and compare what you find against the task's own list; the sweep also surfaces the cases that must NOT be touched, which re-reading the task cannot.
- **Its destination** — a stale measurement of a source keeps the work's shape; a stale measurement of a destination can INVERT the operation with nothing in the description looking wrong. A move is a claim about two files, and a description can only have checked the one its author was holding.

Two more reads belong here. Check `.state/workstreams/ARCHIVE.md` for a closure that already produced what the task proposes to produce — the ledger is the one file that indexes what other workstreams finished, and nothing else in the working path points at it. And where the description asserts a measured fact, re-measure by a DIFFERENT method than the one the task names — re-running the same pattern reproduces the same wrong answer. And read the OTHER LIVE workstreams for an open task that already owns the same artifact: `workstream-record.py cites <project root> <the artifact's name -- its file, script or mechanism, not the task's ID>` across the state tree, and on an open hit decide which task owns the work BEFORE building, tombstoning the other with a pointer — one fix was built and checked under a fresh task while an older task in another workstream had owned the identical change for a week with a fuller verification clause, and the owner surfaced only at capture. One sweep per task start is the whole cost.

Expect the re-derivation to change what the work IS — in one backlog every task carrying a measurement was wrong, in both directions, whatever its provenance — so re-derive as the first step of the work, not as a safeguard against surprise. Read a Decision you are about to build on the same way, and an incoming handoff's framing too. A task whose premise is a menu of candidate remedies — a Learning's, a sender's, or the option list this session wrote into the task line — verifies the MENU as a claim about the problem's shape before weighing its entries — five of twenty evaluations decided at one sitting had an option list that was itself the defect. Which check each kind of claim wants is the rule's section of that name; pick from it rather than re-reading the description.

## Derive the goal condition

**Scope.** Identify the critical path through the open backlog (the ordered tasks that unblock the rest); if it is not derivable from the backlog, that is a drift signal — recommend `/workstream-review` first. Then choose the unit, and default to the LARGEST unit on the critical path whose members are all either/or-completable (below) and none of which is budget-sensitive; fall back to a single task otherwise. Three shapes are always available — one task, a cluster ending at a gate recommendation, a run of critical-path tasks needing no gate — and the single task is the cheapest to satisfy, which is why sessions default to it when they have context for more. A budget-sensitive task is one an auto-compact would strand half-done, and the test is RESUMABILITY, not size: an operation whose units commit independently and whose tool resumes an interrupted run is never budget-sensitive, while one that lands as a single commit is, however small. A budget-sensitive task wants a fresh session; never bundle quick tasks with one such build.

**The principle.** A condition holds at the moment the session tries to stop, and pre-commits to nothing the work may invalidate. State it BY OUTCOME, NEVER BY REFERENT: an outcome is what must be true of the work; a referent is something that must exist or occur outside it — an action performed, an identifier that resolves, a file at a path, a mechanism in the code. The evaluator runs at the end of every turn, a met goal clears itself, a new `/goal` replaces an armed one, and the session cannot see whether one is armed — so a clause that a correct action makes false stays unsatisfiable until the user clears or replaces the goal. Drafting test: if a reasonable implementation of this task would make the clause false, the clause names a referent. The shapes it has taken, each from a session that did the right thing and could not stop, with the phrasing that fixes each:

- An imperative read as a halting requirement: "Stop at user gates" — say the property, "auto-passes no user gate".
- A shared-visible action named at all: "The push runs only on the user's explicit go" — say "the push is surfaced as its own gate"; a held gate can still need `/goal clear`.
- A mechanism the session checked minutes earlier: "Function F carries value V", or a count that holds only while the gate is open — say the outcome, "the room's policy ships unrecorded".
- An identifier that must resolve: "#XX-15 is checked with its commit cited" — say "the report is fully dispositioned and whichever task owns it is checked".
- A path that stops existing: a closure condition naming the workstream's own `workstream.md` — say the durable facts, the criteria verified and the gate presented; the commit survives the archive, the path does not.

**Either/or completion is the default shape.** For every task a condition covers: "the task is either checked with its commit cited, or blocked with the blocker recorded in workstream.md and state committed" — a finished build satisfies it, an honest stop satisfies it, and giving up quietly does not, which is what makes a larger scope safe. A gate is phrased the same way — "presented at #G-XX with a substantive summary" — which holds whether the gate is still open or already decided. Templates:

- Task: "The work #XX-N names is done and committed (cite the commit) with whichever task owns it checked in workstream.md, or blocked with the blocker recorded there; ACTIVE.md is advanced past it; state files are committed."
- Cluster or phase: "Every XX-phase work task is either checked with a committed artifact or blocked with its blocker recorded (`grep -cE '^ *- \[ \] #XX-' workstream.md` returns 0 measures the finished half — it counts work tasks only, since `#G-XX` is not matched by `#XX-`, so it stays true whether the gate is open or already decided); the session presents #G-XX with a substantive summary; state files are committed."
- Build with tests: "<test command> exits 0 and the change is committed, or the failing run and its diagnosis are recorded in workstream.md; state files are committed."

**Mechanical checks, measuring end state.** Prefer a check over a judgement, and constrain what it MEASURES: a count over the open-task pattern returning 0 measures the finish line, while a check that asserts the world's shape before the work has looked is a referent in mechanical clothing. A count of THE BACKLOG is the same trap one step closer, because the session itself mutates the backlog — a probe phase that wrote its follow-on work down registered as a failure to finish — so a condition that counts open items carries an exception for items minted after it is armed, and a probe or research phase gets a condition naming the ARTIFACTS it must produce rather than one counting what remains open.

**Always include** the state-commit clause; "without compromising requirements; auto-passes no user gate"; and the escape clause with both of its bounds, turns and context — "or, if blocked, not converging after ~N turns, or the context budget nears its threshold, checkpoint state and stop with a status report" — roughly 20 turns for a single task, 50 for a phase. The escape clause bounds effort; it does not release the hook on its own — the either/or shape is what makes the stop satisfiable. If the loop does start anyway, hold the engineering call, verify the deferral premise, and wait for the user to clear the goal; never execute a deferred build to silence the hook. One condition, short enough to read whole at every stop check.

**An unattended `/goal` is the caution, not an interactive one.** A goal over user-gated work does not churn while the user is answering; what it cannot do is finish while the user is away. For such work phrase the condition as "drafted, with forks flagged for the gate" or "presented at #G-XX" — never "finalized" or "decided", which only the user's answers satisfy — and say that `/goal clear` exists if the user wants the hook off before the condition is met.

Summarize in chat what reaching the condition will **achieve against the backlog** — which tasks close, what artifact lands, which gate the session stops at, and what state the workstream is in afterward — never the condition's own wording, which answers a question the user did not ask. Hold the condition text itself back until they choose. That summary has to be **visible before the choice**: finish every tool call for this stage first, so the summary opens the message that carries the AskUserQuestion and nothing follows it but the question, and carry the facts that must reach the user inside the `question` field as well, which renders with the menu by construction.

Then ask the user how to proceed, with AskUserQuestion — but only when the unit is a task, cluster or phase to be worked without the user; a gate unit proceeds interactively on the outcome summary alone. Skip the question too when the user has said a goal is armed this session, which the session cannot see for itself. The options:

- **Copy to clipboard** (recommended): on selection, place the full `/goal <condition>` on the clipboard (`pbcopy` on macOS) **and** print that same text in the chat in a fenced code block. Where no clipboard tool exists, the fenced block is the delivery.
- **Process interactively**: work toward the condition now, in this session, without arming a `/goal` hook.
- **Refine the goal together**: adjust scope, checks, or the turn bound before committing to it.

Never touch the clipboard until the user selects **Copy to clipboard** — it is a shared resource that may hold unrelated content. On selection, the clipboard and the fenced block carry the exact same text — a mis-pasted condition is unenforceable. Do not set the goal yourself; `/goal` is the user's to issue.

## Autonomous boundaries

- Reads, edits, sub-agent delegation: proceed.
- Commits and state updates: proceed, one logical unit per commit so each is independently reversible.
- Deferred decisions ("X vs Y, decide during this task"): take the reversible side, record the rationale at the decision site, flag for the next gate.
- `#G-` checkpoints: STOP with a substantive summary and the evidence. Never auto-pass.
- Shared-visible or irreversible actions (pushing to shared remotes, opening PRs/issues, deleting non-session files, scope changes): STOP and surface, unless standing authorization names the specific action.

A gate holding more than one DEPENDENT decision — where an answer can change another item's question — or any gate that has already drawn a clarification request, is presented as a sequenced dialogue, not one bundled question: one question per dimension, each preceded by its own prose setup (context, stakes, recommendation, pros and cons against the alternatives), each answer reflected back with the assumption it rests on named, each answer allowed to shape the next question, and a free-text answer respected as a reframe rather than forced into the offered options. Sequencing lets dissent land while it can still change the questions downstream of it; a bundled form resolves every dimension against a single framing that the first answer would have invalidated, and a better summary alone does not fix that. Where the items are weighed against a budget — always-loaded bytes, a word count — each question carries the item's cost and the running total against the budget: fourteen per-item verdicts, each right, still breached the budget the gate named as governing, because no question showed the sum. INDEPENDENT items get one message carrying every item's analysis and recommendation, with its target text read and its measurement re-run, and a single multi-select asking which the user wants to discuss one at a time; the rest are taken as recommended, and each is still recorded with its own rationale. Fifteen independent items drew fifteen round trips, every one answered with the recommendation, as did sixty-one before them.

## Delegate; claim with evidence

Whenever one agent is handed another's specification, hand it the originating text VERBATIM and add checks on top — a paraphrase drops the allowances the original granted, and the receiving agent reports them as deviations. The packet discipline covers the session's own edits too: a file's own check — `sh -n` for a shell script, `python3 -m py_compile`, the suite that reads it — runs before the commit that carries it.

- **scout** — read-only reads where reading beats a command: opening every line a draft cites, checking a statement against the files it describes, an inventory that takes judgment to assemble. A count, a staleness date, or any grep-shaped record is derived by command in main context — `workstream-record.py` for the state tree — where it is exact and cheap. A scout's inventory is a starting hypothesis, not the punch list: verify cited line numbers before editing from them, and for an exhaustive-edit sweep read the target files in full and run an independent `cites --repo` (or `grep -rn` for the non-markdown files, which `cites` does not read) across the whole surface, references/ subdirectories included — a scout scoped to the primary files under-reports.
- **worker** — bounded packets only: objective, file scope, verification command, stop conditions. Never open-ended. A packet's NEGATIVE checks are each stated as their own check — a failure branch is unverified until it fires — and each asserts the fixture state it assumes before it fires and matches the failure it expects rather than any failure.
- **verifier** — fresh-context check of worker output against its packet, verbatim, before you accept it. Run it after the packet's worker has finished and before the NEXT packet's worker starts, or scope any "X is the only new file" check to named paths — a verifier running concurrently with the following worker fails the scope check falsely.

Every "done" claim cites its evidence: a commit hash, a passing command's output, a count. No evidence, no checked checkbox. Findings from sub-agents — and the LIMITATIONS a sub-agent states about them — are inputs to verify, not conclusions to repeat: an overstated limitation costs the same re-derivation as an understated one and draws less scrutiny, because it reads as honest hedging.

## Session exit

Run the capture sweep (workstreams-rule) over the session against the durable files — detection / cascade / synthesis — and route each finding; capture should not depend on the user asking. Then check off completed tasks with one-line evidence notes, update ACTIVE.md (task, Now, Next, Blockers), and commit state files. Name every reference that crosses a workstream or project boundary with a few words saying what it is (workstreams-rule, Task IDs), in ACTIVE.md and in what you say to the user alike. Checking off a task can resolve a Learning: `workstream-record.py cites <project root> "#XX-N" --section Learnings` lists the Learnings naming it, and any whose integration target is the task being closed gets its disposition marker in the same commit — a never-closing workstream extracts each Learning the moment it resolves, and this is that moment.

ACTIVE.md may never refer to a goal it does not contain. If a condition was drafted but never armed, record the SCOPE it covered — the task or phase, and the turn bound — not "the drafted goal", since the draft dies with the session and scope is what re-deriving the condition needs anyway. If the session ends with a gate still open, ACTIVE.md Blockers names the gate; if the user decided a gate this session, record it (check #G-XX with the decision's provenance) and advance ACTIVE.md past it -- never revert a recorded user decision to satisfy a /goal hook, use /goal clear instead.
