# Workstream Work

Read `.state/ACTIVE.md` and the active `workstream.md` first, then announce "Resuming <name> at <task>". If the session-start hook reported a staleness signal, reconcile before any task work: update the state to match reality, set `status: paused`, or start `/workstream-close`, which stops at its own gate. If the backlog no longer reflects the accumulated Decisions and Learnings, or the critical path is not derivable from it, run `/workstream-review` before working: its restructures are user-gated, so running it commits nothing on its own, while a drifted backlog worked as written does.

If ACTIVE.md refers to a goal drafted by an earlier session, treat the reference as unverified until you find the condition: a condition that was copied to the clipboard but never armed lived only in that session's chat and did not survive the boundary. Say plainly that the draft is unrecoverable and derive a fresh condition — never redraft silently, which turns a lost draft into an invisible scope change. Write-side, this reference should not exist in the first place: see the ACTIVE.md rule under Session exit.

## Verify the task against the world

A task description is a dated claim about the world, and the first step of working one is re-reading the world it describes — the named artifacts, not the backlog's wording. Do it BEFORE drafting the goal condition, because a condition drafted against the description inherits whatever the description got wrong. Three kinds of claim, and the second and third are the ones that read as given rather than as asserted:

- **What it names** — a file, a count, an audience size, a platform behaviour. Re-read each against the artifact.
- **Its scope** — a task's list of what it touches asserts a blast radius, and because it reads as scope rather than as a claim it is the line least likely to be re-checked. Sweep the tree for the thing being changed and compare what you find against the task's own list. The sweep also surfaces the cases that must NOT be touched — a document quoting another system's historical behaviour, say, which a name-matching pass would rewrite into a false claim — and no amount of re-reading the task would reveal those.
- **Its destination** — a stale measurement of a source inflates or deflates an estimate and the work keeps the shape you expected; a stale measurement of a destination can INVERT the operation with nothing in the description looking wrong. A "move" whose destination has since absorbed most of the source is a delete plus a small remainder, and worked as written it re-imports what the destination already holds. A move is a claim about two files, and a description can only have checked the one its author was holding.

Two more reads belong here. Check `.state/workstreams/ARCHIVE.md` for a closure that already produced what the task proposes to produce — the ledger is the one file that indexes what other workstreams finished, and nothing else in the working path points at it, so a baseline gets re-derived with nothing to compare against. And where the description asserts a measured fact, re-measure by a DIFFERENT method than the one the task names: re-running the same pattern reproduces the same wrong answer.

Expect the re-derivation to change what the work IS, often enough that scoping before measuring is the actual error: in a backlog where every task carrying a measurement was re-derived, every one was wrong, in both directions. Provenance does not predict it — a task from a handoff, from a prior session, or from this workstream's own creation interview goes stale the same way — so re-derive as the first step of the work, not as a safeguard against surprise. Working a description blind redoes it, over-scopes it, or aims it at the wrong artifact. Read a Decision you are about to build on the same way, and an incoming handoff's framing too — the sending project may have superseded it before you got there. A task whose premise is a menu of candidate remedies — a Learning's, a sender's, or the option list this session wrote into the task line — verifies the MENU as a claim about the problem's shape before weighing its entries: three remedies all presumed one problem where the tree held two, in opposite directions, and any pick from the list would have shipped half a fix; of twenty evaluations decided at one sitting, five had an option list that was itself the defect, with the right answer on none of them. This is the working-side analogue of review's "verify a Learning against the named file". Which check each kind of claim wants is the rule's section of that name; pick from it rather than re-reading the description.

## Derive the goal condition

**Scope.** Identify the critical path through the open backlog (the ordered tasks that unblock the rest); if it is not derivable from the backlog, that is a drift signal — recommend `/workstream-review` first. Then choose the unit, and default to the LARGEST unit on the critical path whose members are all either/or-completable (below) and none of which is budget-sensitive; fall back to a single task otherwise. Three shapes are always available — one task, a cluster of tasks that ends at a gate recommendation, a run of critical-path tasks that need no gate — and the single task is the cheapest to satisfy, which is why sessions default to it when they have context for more. A budget-sensitive task is one an auto-compact would strand half-done — a migration, a regeneration of committed test vectors — and it wants a fresh session rather than the tail of a spent one; never bundle quick tasks with one such build.

**The principle.** A condition holds at the moment the session tries to stop, and pre-commits to nothing the work may invalidate. State it BY OUTCOME, NEVER BY REFERENT. An outcome is what must be true of the work; a referent is something that must exist or occur outside it — an action performed, an identifier that resolves, a file at a path, a mechanism in the code. The evaluator runs at the end of every turn, a met goal clears itself, a new `/goal` replaces an armed one, and the session cannot see whether one is armed — so a clause that a correct action makes false stays unsatisfiable until the user clears or replaces the goal. Drafting test: if a reasonable implementation of this task would make the clause false, the clause names a referent.

The shapes it has actually taken, each from a session that did the right thing and could not stop:

- **An imperative read as a halting requirement.** "Stop at user gates" fails the moment the user answers the gate in-session, because the evaluator weighs it above the outcome phrasing beside it. Say the property instead: "auto-passes no user gate".
- **A shared-visible action named at all.** "The push runs only on the user's explicit go" constrains execution, and the evaluator read it as mandating the push, then cited the user's own decision to hold as the failure. Say: "the push is surfaced as its own gate". The evaluator is not the kit's, so a held gate can still need `/goal clear`; the wording is the part in your hands.
- **A mechanism the session checked minutes earlier.** "Function F carries value V" was verified against the source before drafting, and the work then found F served a second caller nobody had ruled on, so the right change left F alone. Verifying where a value lives establishes that, not that it is the right seam to change. The same trap in mechanical clothing: a count that holds only while the gate is open, "Next names #G-XX", "24 remaining references". Say: "the room's policy ships unrecorded".
- **An identifier that must resolve.** "#XX-15 is checked with its commit cited" — and mid-session #XX-15 turned out to duplicate a task that had owned the work for two weeks. The work was done once under the owner and the duplicate tombstoned; satisfying the clause would have taken an empty commit or an artificial split, a false record written to match a string. The hook was right to reject. Say: "the report is fully dispositioned and whichever task owns it is checked".
- **A path that stops existing.** A closure condition naming the workstream's own `workstream.md` holds right up until the user approves closure, and the archive step deletes the file. Say the durable facts — the criteria verified with evidence recorded and committed, the gate presented with a substantive summary — never the file still at its path. The commit survives the archive; the path does not.

**Either/or completion is the default shape.** For every task a condition covers: "the task is either checked with its commit cited, or blocked with the blocker recorded in workstream.md and state committed". A finished build satisfies it, an honest stop satisfies it, and giving up quietly does not, since the blocked branch still demands a recorded blocker. This is what makes a larger scope safe: every member resolves either way, so a build correctly deferred at 43% context, or a task found on reading to contradict an approved requirement, ends the session cleanly instead of leaving it looping. A gate is phrased the same way — "presented at #G-XX with a substantive summary" — which holds whether the gate is still open or the user approved it and the shared-visible steps ran: the goal is "reached the gate", not "never pushed". Templates in that shape:

- Task: "The work #XX-N names is done and committed (cite the commit) with whichever task owns it checked in workstream.md, or blocked with the blocker recorded there; ACTIVE.md is advanced past it; state files are committed."
- Cluster or phase: "Every XX-phase work task is either checked with a committed artifact or blocked with its blocker recorded (`grep -cE '^ *- \[ \] #XX-' workstream.md` returns 0 measures the finished half — it counts work tasks only, since `#G-XX` is not matched by `#XX-`, so it stays true whether the gate is open or already decided); the session presents #G-XX with a substantive summary; state files are committed."
- Build with tests: "<test command> exits 0 and the change is committed, or the failing run and its diagnosis are recorded in workstream.md; state files are committed."

**Mechanical checks, measuring end state.** Prefer a check over a judgement, and constrain what it MEASURES: `grep -c` over the open-task pattern returning 0 measures the finish line and cannot be falsified by learning something new, while a check that asserts the world's shape before the work has looked — a count of remaining references, the name of an API surface the work is meant to build on — is a referent in mechanical clothing. A count of THE BACKLOG is the same trap one step closer, because the session itself mutates the backlog: a probe phase that did its job and wrote the follow-on work down pushed its open count from zero to one, and the session's own discovery registered as a failure to finish. The pressure is the defect — the cheap escapes are leaving the discovered task unwritten or renumbering it into another phase, which is renaming a thing to satisfy a grep — so a condition that counts open items carries an exception for items minted after it is armed, and a probe or research phase, whose job is to discover work, gets a condition naming the ARTIFACTS it must produce (each question answered, each reference written) rather than one counting what remains open.

**Always include** the state-commit clause; "without compromising requirements; auto-passes no user gate"; and the escape clause with both of its bounds, turns and context — "or, if blocked, not converging after ~N turns, or the context budget nears its threshold, checkpoint state and stop with a status report" — roughly 20 turns for a single task, 50 for a phase. The escape clause bounds effort; it does not release the hook on its own, since the evaluator can agree the fallback was met and still rule another clause unmet — the either/or shape is what makes the stop satisfiable. If the loop does start anyway, hold the engineering call, verify the deferral premise, and wait for the user to clear the goal; never execute a deferred build to silence the hook. One condition, short enough to read whole at every stop check.

**An unattended `/goal` is the caution, not an interactive one.** The evaluator runs at each turn end and a met goal clears itself, so a goal over user-gated work — sudo passwords, GUI steps, device approvals, biometric taps, a co-design session that runs gate-to-gate — does not churn while the user is answering; three sessions observed no churn across their gates. What it cannot do is finish while the user is away: a clause only a gate answer satisfies sits unmet overnight, bounded only by the escape clause's turn count. For such work phrase the condition as "drafted, with forks flagged for the gate" or "presented at #G-XX" — never "finalized" or "decided", which only the user's answers satisfy — and say that `/goal clear` exists if the user wants the hook off before the condition is met.

Summarize in chat what reaching the condition will **achieve against the backlog** — which tasks close, what artifact lands, which gate the session stops at, and what state the workstream is in afterward. Do not summarize the condition's own wording: the user is deciding whether that outcome is the right scope for the session, and a paraphrase of the goal text answers a question they did not ask. Hold the condition text itself back until they choose.

That summary has to be **visible before the choice**: finish every tool call for this stage first, so the summary opens the message that carries the AskUserQuestion and nothing follows it but the question. Where a fact must reach the user with the menu — which tasks close, what artifact lands, where the session stops — carry it inside the `question` field as well, which renders with the menu by construction.

Then — unless the user has said a goal is armed this session, which the session cannot see for itself — ask the user how to proceed, with AskUserQuestion:

- **Copy to clipboard** (recommended): on selection, place the full `/goal <condition>` on the clipboard (`pbcopy` on macOS) **and** print that same text in the chat in a fenced code block, so the user can paste from either. Where no clipboard tool exists, the fenced block is the delivery.
- **Process interactively**: work toward the condition now, in this session, without arming a `/goal` hook.
- **Refine the goal together**: adjust scope, checks, or the turn bound before committing to it.

Never touch the clipboard until the user selects **Copy to clipboard** — it is a shared resource that may hold unrelated content, so neither the outcome summary nor the question itself may write it. On selection, the clipboard and the fenced block carry the exact same text — a mistyped or mis-pasted condition is unenforceable. Do not set the goal yourself; `/goal` is the user's to issue.

## Autonomous boundaries

- Reads, edits, sub-agent delegation: proceed.
- Commits and state updates: proceed, one logical unit per commit so each is independently reversible.
- Deferred decisions ("X vs Y, decide during this task"): take the reversible side, record the rationale at the decision site, flag for the next gate.
- `#G-` checkpoints: STOP with a substantive summary and the evidence. Never auto-pass.
- Shared-visible or irreversible actions (pushing to shared remotes, opening PRs/issues, deleting non-session files, scope changes): STOP and surface, unless standing authorization names the specific action.

A gate holding more than one decision — or any gate that has already drawn a clarification request — is presented as a sequenced dialogue, not one bundled question: one question per dimension, each preceded by its own prose setup (context, stakes, recommendation, pros and cons against the alternatives), each answer reflected back with the assumption it rests on named, each answer allowed to shape the next question, and a free-text answer respected as a reframe rather than forced into the offered options. Sequencing lets dissent land while it can still change the questions downstream of it; a bundled form resolves every dimension against a single framing that the first answer would have invalidated, and a better summary alone does not fix that.

## Delegate; claim with evidence

Whenever one agent is handed another's specification — the verifier its worker's packet, a worker a packet built from a scout's inventory or from a gate summary — hand it the originating text VERBATIM and add checks on top. A paraphrase drops the allowances the original granted, and the receiving agent reports them as deviations, which read as real findings rather than as a spec mismatch.

- **scout** — read-only reads where reading beats a command: opening every line a draft cites and saying whether it reads as claimed, checking a statement against the files it describes, an inventory that takes judgment to assemble. A count, a staleness date, or any grep-shaped record is derived by command in main context, where it is exact and cheap. A scout's inventory is a starting hypothesis, not the punch list: verify cited line numbers before editing from them, and for an exhaustive-edit sweep read the target files in full and run an independent `grep -rn` across the whole surface (including references/ subdirectories) — a scout scoped to the primary files under-reports.
- **worker** — bounded packets only. A packet states: objective, file scope, verification command, stop conditions. Never open-ended. A packet's NEGATIVE checks — the cases the deliverable must reject — are each stated as their own check, because a failure branch is unverified until it fires. Each negative check also asserts the fixture state it assumes before it fires, and matches the failure it expects rather than any failure: a setup step that fails silently leaves the previous state in place, and where every branch exits non-zero the wrong branch's failure reads as the right one.
- **verifier** — fresh-context check of worker output against its packet, verbatim, before you accept it. Run it after the packet's worker has finished and before the NEXT packet's worker starts, or scope any "X is the only new file" hygiene check to named paths: a verifier running concurrently with the following worker sees that worker's file land mid-check and fails the scope check falsely while every content check passes.

Every "done" claim cites its evidence: a commit hash, a passing command's output, a count. No evidence, no checked checkbox. Findings from sub-agents — and the LIMITATIONS a sub-agent states about them — are inputs to verify, not conclusions to repeat: a caveat that overstates a limitation ("dash absent, so the POSIX claim is unproven", with dash at `/bin/dash`) costs the same re-derivation as one that understates it, and draws less scrutiny because it reads as honest hedging.

## Session exit

Run the capture sweep (workstreams-rule) over the session against the durable files — detection / cascade / synthesis — and route each finding; capture should not depend on the user asking. Then check off completed tasks with one-line evidence notes, update ACTIVE.md (task, Now, Next, Blockers), and commit state files. Name every reference that crosses a workstream or project boundary with a few words saying what it is (workstreams-rule, Task IDs), in ACTIVE.md and in what you say to the user alike. Checking off a task can resolve a Learning: grep the Learnings for the task's ID, and any Learning whose integration target is the task being closed gets its disposition marker in the same commit — a never-closing workstream extracts each Learning the moment it resolves, and this is that moment.

ACTIVE.md may never refer to a goal it does not contain. If a condition was drafted but never armed, record the SCOPE it covered — the task or phase, and the turn bound — not "the drafted goal": the draft dies with the session, and a state file that points at it makes a claim the next session cannot verify. Scope is what re-deriving the condition needs anyway, and it is one line rather than the whole condition. If the session ends with a gate still open, ACTIVE.md Blockers names the gate; if the user decided a gate this session, record it (check #G-XX with the decision's provenance) and advance ACTIVE.md past it -- never revert a recorded user decision to satisfy a /goal hook, use /goal clear instead.
